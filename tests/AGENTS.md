# tests/AGENTS.md

- Use the applicable `code-testing-agent` skill when adding tests; use the matching test-analysis skill for audits. Test only meaningful observable behavior, with independent expectations; avoid assertions that cannot catch a real defect or merely repeat the implementation.
- For new tests, demonstrate that a meaningful behavior break makes the test fail, restore the code, and report the check. Live verifier negative controls below satisfy this rule for the live scenario.
- Use synthetic text, identities and values only. Never commit real messages, credentials, sessions or private evidence. Regular tests must not call providers or use real credentials.
- Database tests must use an isolated disposable database, never the home database. Verify persistence and duplicate-source constraints against real PostgreSQL when behavior depends on them.
- The first live scenario must identify the exact revision and synthetic expectation, verify exact row count, value, unit, subject and source, restart the process, then verify deterministic Telegram readback. The same verifier must reject synthetic missing rows, wrong values and wrong sources locally. One successful bounded live scenario is sufficient; preserve failures and distinguish skipped, unavailable and failed checks.
- Use a reproducible runner in this repository and keep secrets, session files and raw evidence outside repositories. Only the designated owner controls the shared Telegram MCP session. Do not open another session or poller with the same identity or bot. Never touch the home containers, runtime or data as a test fixture.
